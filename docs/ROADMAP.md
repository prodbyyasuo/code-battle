# План разработки Code Battle

## Что берём из исходных проектов

Из `code_versus` сохраняем предметную идею и границы данных:

- аккаунты, задачи, отправки и агрегированные результаты относятся к основному API;
- закрытые тест-кейсы относятся к judge-подсистеме и MongoDB;
- длительные действия выполняются вне HTTP-запроса;
- фронтенд общается только с API.

Из `real-crm-project` сохраняем понятное разделение `route → service → repository`,
Pydantic-настройки, lifespan FastAPI, dependency injection и тестирование слоёв.

Не переносим технический долг исходника: синхронный ORM, блокирующий RPC, запуск
пользовательского кода рядом с API, потоки на каждый тест, хранение секретов в
настройках и смешивание transport/domain/storage логики.

## Целевая схема

```text
React client
    │ HTTP/JSON
    ▼
FastAPI API ─────────────── PostgreSQL
    │                         users, tasks, submissions,
    │ enqueue                  attempts, result summaries
    ▼
Redis / Celery
    │
    ▼
Judge orchestrator ───────── MongoDB
    │                         private test cases, test revisions
    ▼
Isolated runner containers
```

На первом проходе это модульный монолит плюс отдельный worker/judge. Дробить всё на
микросервисы заранее не нужно: границы уже будут видны в пакетах и контрактах.

## Этап 0 — инфраструктурный фундамент (готово)

- [x] Python 3.14 и окружение `uv`.
- [x] Runtime/dev зависимости и зафиксированный `uv.lock`.
- [x] Multi-stage Dockerfile для development и production.
- [x] Compose с API, PostgreSQL, MongoDB и Redis, health checks и volumes.
- [x] `.gitignore`, `.dockerignore`, `.env.example`.
- [x] Минимальный `/health`, чтобы инфраструктуру можно было проверить до бизнес-кода.

## Этап 1 — каркас FastAPI (следующий)

Твоя задача:

1. Создать пакет `app` с модулями `main.py`, `core/config.py`, `api/router.py`,
   `db/postgres.py`, `db/mongo.py`. В каждом Python-каталоге, который является
   пакетом, добавить `__init__.py`.
2. Перенести создание приложения в фабрику `create_app()`.
3. В `core/config.py` хранить только типизированные настройки. SQLAlchemy engine и
   session factory определить в `db/postgres.py`, используя
   `settings.database_url`; не создавать сетевые ресурсы внутри `Settings`.
4. В lifespan инициализировать один async SQLAlchemy engine, один
   `AsyncMongoClient` и один async Redis client; на shutdown корректно закрыть их.
5. Сделать `/health/live` без внешних проверок и `/health/ready` с `SELECT 1`, Mongo
   `ping` и Redis `ping`.
6. Подключить единый обработчик доменных ошибок и request-id middleware.

Критерий готовности: приложение стартует локально и в Compose, readiness становится
успешным только после готовности всех хранилищ, Ruff/mypy/pytest зелёные.

## Этап 2 — PostgreSQL и Alembic

1. Настроить `AsyncEngine`, `async_sessionmaker` и dependency с короткой сессией на
   запрос; не держать транзакции во время сетевых вызовов.
2. Создать общий declarative base с UUID, `created_at`, `updated_at` и UTC-aware датами.
3. Спроектировать первые модели: `User`, `Problem`, `Submission`, `SubmissionCase`.
4. Инициализировать Alembic с async-шаблоном, создать и вручную проверить первую
   миграцию.
5. Добавить уникальные ограничения и индексы исходя из запросов, а не «на всякий
   случай».

Критерий готовности: чистая БД поднимается командой `alembic upgrade head`, downgrade
проверен на локальной БД, тесты репозиториев изолированы.

## Этап 3 — MongoDB и модель тест-кейсов

1. Использовать `pymongo.AsyncMongoClient`, без Motor и без ODM на старте.
2. Описать Pydantic-документы `TestCase` и `TestCaseSet`; наружу не возвращать
   ожидаемые ответы закрытых тестов.
3. Создать repository-интерфейс и реализацию PyMongo.
4. Создать уникальный индекс `(problem_id, revision, ordinal)` и нужные lookup-индексы.
5. Ввести собственные последовательные миграции Mongo: каталог `mongo_migrations`,
   коллекция применённых версий, идемпотентные операции `up`.

Важно: Alembic управляет только SQLAlchemy/PostgreSQL. MongoDB не имеет схемы DDL,
поэтому её индексы и преобразования документов версионируются отдельно.

## Этап 4 — пользователи и безопасность

1. Регистрация и хеширование пароля Argon2 через `pwdlib`.
2. Access/refresh JWT с `sub`, `type`, `jti`, `iat`, `exp`; разные сроки жизни и
   невозможность использовать refresh как access.
3. `/me`, роли `user/admin`, подтверждение email и сброс пароля.
4. Email отправлять через Celery; HTTP-ответ не должен ждать SMTP.
5. Rate limit для auth endpoints и нейтральные ответы, не раскрывающие существование
   email.

## Этап 5 — каталог алгоритмических задач

1. CRUD для админа и read-only выдача пользователю.
2. Сложность, лимиты времени/памяти, поддерживаемые языки, теги и версия условия.
3. Фильтры и cursor pagination.
4. Публичные примеры отделить от закрытых тестов в MongoDB.
5. Покрыть route/service/repository unit- и integration-тестами.

## Этап 6 — submissions и judge

1. `POST /problems/{id}/submissions` создаёт запись со статусом `queued` и ставит
   только идентификатор отправки в очередь.
2. Celery worker загружает снапшот задачи и тестов, затем передаёт запуск отдельному
   judge/runner.
3. Ввести явную машину состояний: `queued → running → accepted|wrong_answer|tle|mle|re|system_error`.
4. Обновления должны быть идемпотентными; повторная доставка Celery не создаёт второй
   результат.
5. API отдаёт статус polling-эндпоинтом; WebSocket/SSE добавляется только после
   рабочей базовой версии.

Критически важно: никогда не выполнять присланный код через обычный `subprocess` в
API/worker-контейнере. Runner получает CPU/memory/PID/time limits, read-only filesystem,
отключённую сеть, non-root user, seccomp/AppArmor и одноразовое окружение. Для первой
учебной версии можно поддержать только Python.

## Этап 7 — профиль и соревнование

1. История отправок, число решённых задач и статистика по сложности.
2. Рейтинг считать по формализованному правилу, обновлять транзакционно.
3. Подписки пользователей и таблица лидеров.
4. Турниры добавлять после устойчивого judge: правила, участники, окно времени,
   замороженный scoreboard.

## Этап 8 — AI-функции

1. Сначала определить продуктовый контракт: подсказка, разбор сложности или ревью
   решения — не свободный чат без границ.
2. Вынести провайдера за Protocol/adapter, задать timeout/retry и лимит стоимости.
3. Не отправлять секретные тесты и персональные данные модели.
4. Кешировать только безопасные детерминированные ответы; логировать метаданные без
   пользовательского кода.

## Этап 9 — качество и эксплуатация

1. Unit-тесты сервисов, integration-тесты репозиториев, contract-тесты API, отдельные
   end-to-end тесты очереди и judge.
2. CI: `uv sync --locked`, Ruff, mypy, pytest с coverage, проверка Alembic head.
3. Структурированные логи, request/submission IDs, Prometheus-метрики, трассировка.
4. CORS allow-list, trusted hosts, лимиты тела запроса, secret management, backup и
   restore drill для PostgreSQL/MongoDB.
5. Production Compose не считать полноценным оркестратором; для публичного деплоя
   отдельно решить TLS, reverse proxy, обновления и изоляцию runner-узлов.

## Правило совместной работы

Каждый следующий этап делаем небольшими итерациями: сначала я даю тебе задачу,
контракт и критерии приёмки; затем ты пишешь код; после этого я провожу review,
объясняю замечания и предлагаю следующий шаг. Готовый код с моей стороны — только по
твоей явной просьбе или для инфраструктурной/диагностической правки.
